# 全盘重构研究与分阶段升级方案

日期：2026-09-30。状态：研究完成，实施方案待按阶段启动；本文不是重构完成声明。

## 1. 结论与目标

可以全面重构，而且收益不限于来源问题：现有代码存在不安全的 HTML 拼接、表单引用泄漏、内容组件错配、输出边界不一致，以及大文件中 UI、状态、转换、图片处理和导出职责混合的问题。

目标是保留已验收的产品能力，用更清晰、安全、可测试的架构实现：公众号预览、主题与配方、自定义配置、复制 HTML、HTML／长图／分段图导出、排版快照和独立的笔记增强。交互优化以当前已经验收的选择模式为基线，而不是重新引入拥挤控件或大量重复主题。

技术重构与官方目录来源审核是两条独立验收线。MIT 许可允许按其条款使用原代码；本报告不是版权侵权判定。Obsidian 官方目录另有来源与公开同意要求。修改变量名、拆分文件、调整语法或删除来源声明不解决该要求。即使完成全面重构，也不能预先保证当前仓库符合官方关于独立项目的要求。

## 3. 已发现的问题与改造方向

### 3.1 作者信息、二维码和示例内容

`DonateManager` 当前显示维护者 yhwang，却引用与上游相同的打赏和公众号二维码。仅能确认资源相同，不能据此确认二维码账户归属。原作者的示例文案仍在 `templatePreviewModal.ts` 中，如“探索夜半插件的无限可能”。

改造为独立的 About／Help 面板，产品说明与贡献者署名分开；示例使用中立测试文章。维护者已决定最后提供新的二维码；目前保留两处文字占位，不引用旧二维码，不猜测账户、生成替代收款码或主动访问二维码地址。官方目录的资助入口按其提交要求处理。

### 3.2 HTML 安全边界

`DialogueRenderer` 直接把说话人、标题、内容放进 HTML；`GalleryRenderer` 直接把图片路径放进 `src` 属性；转换器和自定义头尾将字符串赋给 `innerHTML`。

本次在内存中编译并调用实际渲染函数，确认输入中的无操作事件属性 `onerror="void 0"` 被保留，图片路径中的引号可以形成额外属性。这是生成字符串检查，未在浏览器执行，不等于已经完成真实宿主攻击验证。

改造要求：普通用户文本使用文本节点；图片和链接地址经过协议／资源路径验证；确需支持的自定义 HTML 在进入预览前清洗，不等复制时才检查。HTML 清洗须保留经过批准的公众号内联排版，不得造成主题失效。对自定义 CSS 和主题 token 增加属性和值校验；旧稿不安全内容应明确提示并可回溯，不静默改写 Markdown。

### 3.3 配置表单取消不完全隔离

`CreateFontModal` 直接引用传入的字体对象；`CreateTemplateModal` 只浅拷贝主题，嵌套 `styles` 仍共享引用。修改后取消，可影响当前内存设置，之后还可能被其他保存动作写入。

本次对实际构造器使用最小 Modal stub 验证：不调用提交函数，修改表单草稿后，原字体名称和原主题嵌套样式均改变。该检查未修改真实 Obsidian 或库文件。

改造为独立、深拷贝草稿，加显式验证和原子提交；取消丢弃草稿，保存失败不关闭或伪装成功。配置字段用描述式表单定义，避免 1,225 行的主题表单重复拼接逻辑。保留现有可编辑字段与未知历史字段，不在重构中缩减能力。

### 3.4 内容匹配与输出一致性

- `converter.ts` 为每个对话／画廊代码块调用 `containers.find(...)`，判断只看代码块是否含冒号或图片标记，并不对应具体解析结果。同一篇多段同类型容器可能重复选择第一段。
- 自定义头尾插入预览根节点，而复制、HTML 导出和图片快照取 `.mp-content-section`，存在预览可见内容不进入导出的边界差异。
- `updatePreview()` 包含异步读取和渲染，但缺少渲染序号／取消控制；切换文章或连续更新时应防止旧任务覆盖新结果。

改造为明确的块 ID 与位置映射、统一文章根节点、完整渲染事务和过期任务丢弃。对头尾确认预期语义后统一纳入或明确标注仅预览，不能继续让用户凭显示推断导出结果。

### 3.5 图片与输出服务

旧图片转码逐张 `fetch`，无显式超时、响应状态／类型／大小检查，失败只写控制台。图片导出已有加载超时和完整离屏快照，保留这些保护并统一到公共资源服务。

改造方向：区分本地库资源、已有 data URI 和远程 URL；远程访问使用适当宿主 API；有界并发、取消、超时、大小限制和按次缓存；失败提供可见报告和明确处理策略。复制失败、离线、403、坏图片、超大图不得无限等待，也不能静默宣称全部成功。

### 3.6 官方审核和依赖

已有上架草稿审核：56 处直接静态样式、10 处不安全 `innerHTML`、13 处设置页标题，共三类 79 个报告位置；这些来自基线 `7482481`，不是本次重新触发的审核。

本次使用 npm 官方 registry 的生产依赖审计，发现 `nanoid` 5.1.5 命中一个高风险依赖条目，包含三个安全公告。当前源码只看到无参 `nanoid()`，因此不把公告中需要外部长度参数的攻击条件视为已经在本插件中证实。应升级修复版本并做 ID／旧数据兼容测试，而非盲目 `npm audit fix --force`。

同时核实最低宿主 API、锁定 SDK／工具链、修正发行标签格式，保留旧 BRAT 标签。UI 样式走 CSS／官方样式 API，导出的文章走经过校验的内联样式，二者不能混为一谈。

参考：[官方目录开发者政策](https://github.com/obsidianmd/obsidian-developer-docs/blob/main/en/Community%20directory/Developer%20policies.md#forks)、[nanoid 安全公告](https://github.com/ai/nanoid/security/advisories/GHSA-xwg4-73v4-xw9w)。

## 4. 目标架构

```text
Obsidian 宿主适配层
  ├─ 笔记读写／事件／资源解析
  ├─ 原生 Markdown 渲染与组件生命周期
  └─ CodeMirror 笔记增强边界
          ↓
应用层：配置仓库、编辑草稿、预览会话、主题试用、渲染任务
          ↓
公众号文章管线：安全 DOM → 内容块／主题／配方 → CanonicalArticle
          ├─ 预览投影：自适应／375px，不回写正文或导出设置
          ├─ 复制／HTML：清洗与校验、资源策略、HTML／纯文本一致
          └─ 图片：完整快照、资源就绪、长图／分段图、有界内存

笔记增强保持独立，不读取公众号主题或配方决定编辑器宽度。
```

`CanonicalArticle` 是完整、可测试的文章 DOM／输出契约，不直接用现有 `ArticleModel` 扁平统计数组作为完整文档树：现有数组按元素类型收集，不能替代原文顺序及嵌套结构。

优先复用官方宿主能力与必要、来源明确的依赖；不因重构额外引入 React、大型富文本编辑器、第二个 Markdown 渲染引擎或后台服务。各业务模块依赖接口，不直接依赖全局静态类或操作工作台控件。

## 5. 分阶段执行与门禁

采用小版本、先 beta 后稳定的升级方式。以下版本安排为建议；不能仅为追求“大升级”立即切到 4.0，也不能覆盖已验收的 3.15.0 发行包。

### P0：基线与来源台账

1. 保存发行哈希、已知库配置结构、主题 ID 和快照样例；仅使用脱敏测试夹具，真实库修改必须另行明确。
2. 建立源码、样式、素材与依赖的逐项来源台账，不把相似度当许可结论。
3. 建立实际功能覆盖表，区分“今天确实能用”“已发现边界缺陷”“未来方案”。
4. 加入真实 DOM 行为测试与安全输入夹具；现有 35 项测试包含较多源码正则断言，不能单独证明运行行为或注入安全。

完成条件：来源范围可定位，旧设置／快照可重复载入，回退基线和用户验收清单明确。

### P1：安全与发行基础（建议 3.15.1-beta → 3.15.1）

1. 引入安全文本／URL／HTML 构建边界，修复对话、画廊、Callout、自定义头尾等不安全入口。
2. 处理适用依赖公告，锁定工具链并核实最低 Obsidian 版本；不批量升级不相关依赖。
3. 修复官方审核阻断规则，保持主题及公众号内联样式；对设置页标题同时保留折叠和搜索行为。
4. 发行标签兼容官方要求，保留既有 `v3.15.0` 及 BRAT 回退安装；不要迁移插件 ID。

完成条件：新增安全测试通过，复制和全部导出样式无回退，本地构建与验证通过，官方后台重新检查技术结果。没有来源同意仍不能标记上架完成。

### P2：配置、草稿与界面基础（建议 3.16.x）

1. 用统一配置仓库和深拷贝草稿替换主题／字体／背景表单的共享引用逻辑。
2. 表单声明式定义、分区验证、取消零副作用、等待提交完成；保存失败有可见反馈。
3. 重建 About／Help 与中立示例；处理维护者确认后的二维码资源与准确贡献者署名。
4. 将 `view.ts` 中控件创建、设置同步、文章状态分拆为独立模块；继续使用原生 Obsidian 控件。

完成条件：保存、取消、校验失败、异步失败、显示偏好、重启加载均有行为测试；既有主题与背景字段无损往返。

### P3：文章管线、资源与输出（建议 3.17.x）

1. 逐段迁移转换器和主题应用器到有顺序、有 ID 的文章处理管线，保留历史适配层直至回归通过。
2. 修复多组件错配、重复增强、头尾输出边界及渲染竞态。
3. 复制、HTML 和图片导出使用同一 `CanonicalArticle`，格式差异仅发生在明确的输出适配器中。
4. 引入资源服务、错误报告、取消和离屏快照回收；继续保留完整长图、分段比例及手机视口不影响导出宽度的约束。

完成条件：同一固定文章在预览、复制、HTML、长图和分段图中的内容、顺序与主题一致；组件多次使用、离线、失败资源和关闭面板均可控。

### P4：呈现、性能与整合（建议 3.18.x）

1. 保留场景选择和纯名称主题卡片，推荐用途仍在选中后的说明区域；历史主题维持小入口。
2. 工具栏按正文外观、主题、输出、次要操作分组，窄宽度逐组换行；次要项进入已有高级区域，保持键盘可达。
3. 设置、主题画廊、表单、帮助、错误／进度反馈统一间距、字号、焦点和暗色样式，CSS 严格作用域隔离。
4. 启动 UI 实施前加载适用设计技能；视觉方案以实际宿主截图验收，不仅检查 CSS 源码。
5. 做多面板、快速文章切换、长文章、低分辨率、不同系统缩放和多库隔离验证。

完成条件：320／375／414px 文章展示及窄工作台无截断、关键操作可用；普通正文对比度不低于 4.5:1；不影响 Obsidian 全局布局或输入。

## 6. 每阶段统一验收与回溯

- 运行构建和 `npm run verify`；补充执行实际 DOM／状态／资源逻辑的测试，不把正则匹配通过当作行为验收。
- 既有主题 ID、自定义主题、字体、背景、历史可见性、布局快照和 `note-layout.json` 不静默丢失或自动覆盖。
- 设置格式变化前有备份、幂等迁移和失败回退；需要回滚的数据必须能由上个稳定版读取或恢复。
- 每阶段独立提交与预发布；真实 Obsidian／BRAT 验收后再稳定发布。记录已测试的宿主版本和平台，不虚称全平台通过。
- 公众号侧至少核对长文、教程、报告的实际粘贴；测试复制、HTML、长图、分段图和主题试用／取消。
- 不修改 Markdown 原文；原有显式编辑图片 alt 的功能仍须由用户操作触发，不能由渲染或迁移自动触发。
- 不加入 AI、图片生成、自动发布或宽表格自动重排，不合并公众号与笔记设置。

## 7. 仍需决定的边界

1. 打赏／公众号二维码的新图片：维护者决定在最后提供，当前使用文字占位。关于页已移除旧资源 import；旧资源文件留在源码／历史中待完整来源清理，不因停止展示就删除版权台账。
2. 官方目录来源路线：保留早期实现并取得可核验公开同意，或另行明确独立项目／独立实现要求并核验。不要把在现有衍生代码上优化等同于无继承的新项目；不自动删除历史署名，不擅自创建新仓库或向原作者发消息。

本次研究完成后，按维护者的明确指示仅把关于页两处二维码改为文字占位，并增加该行为测试；完整架构重构尚未开始。未修改配置、版本号或真实库，未向 GitHub 推送，也未发布新版本或正式上架。后续本地构建用于验证，不覆盖 GitHub 的 3.15.0 发行资产。
